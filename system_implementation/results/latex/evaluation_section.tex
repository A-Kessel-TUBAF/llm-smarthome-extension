\section{Formally verified allocation checking (addition to Section~3.5)}
% =============================================================================

\paragraph{Auditing the proofs.}
That the proofs compile is not by itself evidence that the stated theorems hold:
the Lean compiler accepts any valid proof of any theorem, and it does not know
which theorem was intended, which axioms a project permits, or whether a
definition behind an unchanged statement has been weakened. We therefore audit
the proofs with QED\_LEAF, a fail-closed checker for Lean developments that
re-elaborates the targets and compares them with a protected copy of the
specification. For each target theorem it checks that the proof contains no
unproven step (\texttt{sorry}), that the statement is structurally identical to
the protected reference (statement match), that every definition the statement
depends on is restated identically (definition integrity), that only the
permitted axioms \texttt{propext} and \texttt{Quot.sound} are used (axiom
policy), and that the theorem does not hold vacuously. The audit runs before
every evaluation that uses the checker, and its outcome is recorded with the run.
It takes about 3.5 minutes on a CPU and is cached while the Lean sources,
policy and reference are unchanged; it is not part of request handling, so
task scores and latency are unaffected.

Table~\ref{tab:qedleaf-evidence} contrasts the audit with compilation alone on
four versions of the proofs. All four compile. The audit passes only the current
version; it rejects an earlier version whose soundness and completeness proofs
depended on \texttt{Classical.choice} through a single \texttt{simp} step, a
policy violation that compilation had not surfaced (Table~\ref{tab:qedleaf-axioms}),
and it rejects two deliberately weakened versions, one with a weaker theorem
published under the protected name and one with an independence definition that
drops the exclusive-resource condition. Like the checker's guarantees, the audit
covers only the Lean development; the Python translation remains outside its
scope.

\section{Evaluation}
\label{sec:evaluation}
% =============================================================================

All experiments use Gemma~4 31B~\cite{gemma4} served locally through Ollama
(4-bit quantization, Q4\_K\_M) with thinking disabled, temperature 0 and seed 42,
on a DGX-2 with Tesla V100 (32\,GB) GPUs. The system runs with the Lean checker
admitting every command batch, and the QED\_LEAF audit passed before every run.
We evaluate on the 95 cases of the Home Assistant Assist dataset
(Section~\ref{sec:eval-ha}), the 600 episodes of SimuHome
(Section~\ref{sec:eval-simuhome}), a stratified sample of 1,000 HomeBench test
instructions drawn proportionally to instruction type with seed 42
(Section~\ref{sec:eval-homebench}), and the 100 cases of our own benchmark
(Section~\ref{sec:eval-own}). Each benchmark is scored by its native evaluator.
Table~\ref{tab:gemma4-e2e} summarizes the end-to-end results.

\subsection{Benchmark 1: Home Assistant dataset}
\label{sec:eval-ha}
% -----------------------------------------------------------------------------

The system fulfils 80 of the 95 requests (success rate 0.842). Table~\ref{tab:gemma4-homeassistant}
breaks the result down by device domain: covers, fans, to-do lists and valves succeed in every
case, whereas lights, locks and vacuums, whose requests more often address several entities or
areas at once, lie between 0.67 and 0.71.

\subsection{Benchmark 2: SimuHome}
\label{sec:eval-simuhome}
% -----------------------------------------------------------------------------

Table~\ref{tab:gemma4-simuhome} reports the success rate by query type. State questions (QT1)
are answered correctly in about four of five episodes, whether feasible or not. Workflow
scheduling (QT4) is the weakest type, as the benchmark's authors also observe for other
models~\cite{simuhome}: feasible workflows succeed in 0.26--0.44 of the episodes, and the
system almost never recognizes an infeasible delayed or conditional workflow (QT4-2 and QT4-3
infeasible: one success each in 50 episodes), answering as if the request could be scheduled.

\subsection{Benchmark 3: HomeBench}
\label{sec:eval-homebench}
% -----------------------------------------------------------------------------

On the 1,000-case sample the system reaches an exact match of 0.649 and an operation-level
F1 of 0.703 (Table~\ref{tab:gemma4-homebench}). Single valid instructions and instructions
for non-existent devices are handled well (exact match 0.848 and 0.905), instructions for
unsupported attributes less so (0.696). Multi-step instructions are the weakest type: most of
their individual operations are correct (F1 0.645), but only 0.098 of them are fully correct,
since one wrong or omitted operation fails the whole instruction.

\subsection{Own benchmark}
\label{sec:eval-own}
% -----------------------------------------------------------------------------

Our benchmark has no automatic task score, so we measure which device types the system
involves. Against the device types of all required and acceptable intents, the agents that
were assigned a task reach a precision of 0.955 but a recall of 0.443
(Table~\ref{tab:gemma4-e2e}): the devices the system activates are almost always appropriate,
but it activates too few of them. Restricted to the required intents, recall is 0.502.
Table~\ref{tab:gemma4-classification} separates the model from the system: asked directly
which device types a request involves, Gemma~4 reaches a macro-F1 of 0.909 and covers the
required intents with recall 0.952, whereas the end-to-end system reaches 0.598. The loss
therefore occurs in task decomposition, not in the model's understanding of the request,
which matches the incomplete-decomposition failure pattern of the original system.

\subsection{Limitations of the evaluation}
% -----------------------------------------------------------------------------

Several aspects of the setup qualify the results. (1) Each configuration was
run once, with a quantized model and deterministic decoding; we report no
variance across seeds. (2) SimuHome scores QT1 and all infeasible episodes with
a three-vote LLM judge. We used Gemma~4 31B as the judge, so the model under
test judges its own answers, which may favor it; the judge received complete
prompts (49,152-token context, 1,008 calls, no truncation). The benchmark's
default judge configuration (Gemma~2, 8,192 tokens) cannot read the judge prompts,
which exceed 28,000 tokens, and scored every answer as a failure in a first run
that we discarded. (3) The Home Assistant results are from a rerun after
correcting a harness defect: the adapter's routing argument \texttt{service\_id},
which is not part of Home Assistant's own tool schema, was required but not
defaulted, so 81 of 95 cases failed before planning could complete. The
correction gives the argument its domain as default and does not change the
system's behavior on the other benchmarks, where this error did not occur.
(4) HomeBench was evaluated on a 1,000-case sample, not the full test set of
17,366 instructions. (5) Our own benchmark has no automatic task score; the
reported precision, recall and F1 compare the device types the system assigned
a task with the device types of all required and acceptable intents, so a
system that legitimately selects one interpretation of an ambiguous request
loses recall. (6) The comparison with published results of
HomeBench~\cite{homebench} and SimuHome~\cite{simuhome} is indicative only:
those baselines use older models in single-prompt or ReAct settings, and we
have not yet run Gemma~4 through a plain ReAct agent on the same cases, which
would isolate the contribution of the multi-agent system from that of the
model. (7) The checker's guarantees and the QED\_LEAF audit cover the Lean
development; the translation of agent cards, tasks and observed state into the
checker's input is unverified Python.
